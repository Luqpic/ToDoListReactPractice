# Multi-select & Group Drag-Reorder Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a user right-click a task to enter a multi-select mode, select several tasks, bulk-delete them, or drag one of the selected tasks to reorder the whole selected group together.

**Architecture:** Migrate the task list's drag mechanism from Framer Motion's `Reorder` to `@dnd-kit` (one drag engine for both single-item and group dragging), then layer selection state (`selectionMode`, `selectedIds`) on top: a new right-click context menu enters selection mode, a floating action bar drives bulk actions, and `onDragEnd` moves the whole selected set as a contiguous block.

**Tech Stack:** React 19, `@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities` (new), shadcn `context-menu` (new, built on the project's existing `@base-ui/react` primitives), existing `motion/react` (kept for enter/exit animation only), existing shadcn `AlertDialog`/`Checkbox`/`Button`/`Card`.

**Spec:** `docs/superpowers/specs/2026-09-09-multi-select-drag-design.md` — read it alongside this plan; it has the full rationale for every decision below (approach trade-offs, why the stack-drag visual is simplified, why single-item drag is being migrated at all).

**Testing note:** This project has no automated test suite (no `*.test.*`/`*.spec.*` files, no test script). Every task's "test cycle" is a manual verification pass against a running `npm run dev` server, not an automated test — this replaces the write-test/run-test steps you'd otherwise see here.

## Global Constraints

- Do not change Edit behavior — it stays exclusively on the existing "⋮" popover menu in `task.tsx` (per spec: "Right-click context menu").
- Selection mode always forces `filter = "All"` and `search = ""`, and disables the search/filter inputs, for the duration (per spec: "State & component architecture").
- The stacked-card drag visual is intentionally simplified to a count badge + opacity fade, not a real layered stack (per spec: "Group-drag mechanics & visuals" — user has explicitly agreed to try this first).
- No new automated tests — this repo has none; verify manually per spec's "Testing plan" section.

with:

```tsx
  const handleDragEnd = (event: DragEndEvent) => {
    const { active, over } = event;
    setActiveId(null);
    if (!over || active.id === over.id) return;

    const activeIdNum = active.id as number;
    const overIdNum = over.id as number;
    const isGroupDrag = selectionMode && selectedIds.has(activeIdNum);

    setTask((prev) => {
      const movingIds = isGroupDrag
        ? prev.filter((t) => selectedIds.has(t.id)).map((t) => t.id)
        : [activeIdNum];

      const remaining = prev.filter((t) => !movingIds.includes(t.id));
      const moving = prev.filter((t) => movingIds.includes(t.id));

      const overIndexInRemaining = remaining.findIndex(
        (t) => t.id === overIdNum,
      );
      // Dropping onto another already-selected task (which was just
      // filtered out of `remaining`) falls back to appending at the end.
      // Known first-pass limitation — flagged in the spec for follow-up
      // once this is tried out.
      const insertAt =
        overIndexInRemaining === -1 ? remaining.length : overIndexInRemaining;

      return [
        ...remaining.slice(0, insertAt),
        ...moving,
        ...remaining.slice(insertAt),
      ];
    });
  };
```

                    })()

              </DragOverlay>
